## Что изменилось

### Блок 1. STOP, задача, Live View (FR-01, FR-07.3; NX-052-04/09/10/31)
- **STOP липкий и сохраняется на диске** (`owner-stop.json`): нет таймера (было 10 мин), перезапуск Host его не снимает. Снятие — только `live_control resume` после слов владельца.
- **Остановленная задача не возобновляется сама:** `stopped_by_owner` → новая работа отклоняется; после `resume` — та же задача (`taskResumeAllowed`), `resumes`+1.
- **Live View держится, пока задача открыта:** heartbeat задачи — любой вызов, включая read-only; потолок 10 мин без вызовов → `view_idle` (задача прерывается, но сохраняется). Без задачи (только просмотр) — прежние 45 с → `lease_expired`.
- Статусы различаются: `active / owner_paused / owner_stop / view_idle / lease_expired / idle` (`get_capabilities.state`); в шлюзе — `awaiting_owner_logon / booting / pc_locked / host_offline / tunnel_unavailable / pc_offline_stale_registration`.
- **`stale_args`:** после снятия паузы/STOP и после возобновления прерванной задачи ввод (`mouse/keyboard/browser_action/close/focus`) отклоняется до повторной идентификации цели read-only; ошибка содержит `resumePoint` (что сделано, внешние операции, созданные ресурсы).
- `finish_task` закрывает задачу и без активной сессии; останавливает команды.

### Блок 2. Точечные исправления (FR-02, FR-06)
- NX-052-28: «Очистить/CE/Сброс» в Калькуляторе — без согласия (контекст = приложение без пользовательских данных); сильные слова и диалоги подтверждения — прежняя защита.
- NX-052-29: после закрытия последней вкладки — `{tabs:[],open:false}`, браузер NEXUS закрыт целиком, повторный `list` без `internal_error`, повторное открытие работает.
- NX-052-11 / FR-06.5: каждое `browser_action` → `observed_url`, `observed_state`, `result_verified` (навигация, ввод, выбор, клик/Enter по изменению DOM/URL/фокуса/состояния элемента); ложный `done` помечен.
- Мультимонитор: карта мониторов; при одинаковом масштабе — корректное отображение координат; точка на втором мониторе → `point_on_secondary_monitor`; разный масштаб → `multi_monitor_mixed_dpi_unsupported` (было: любой второй монитор → отказ).
- Буфер обмена: снимок всех форматов, которые Java отдаёт строкой или потоком (HTML, RTF и др., ≤32 МБ) + текст/картинка/файлы; частичное восстановление честно `restored_partial` (`clipboardRestored:false`).
- NX-052-22: точная причина запуска: `exe_not_found`, `requires_elevation_or_access_denied` (UAC — только владелец), `not_a_launchable_exe`.

### Блок 3. Диагностика и команды (FR-03; NX-052-15)
- `system_info` — 13 фиксированных read-only тем (os, hardware+SMART, processes-tree, services, scheduled_tasks, startup, events, network+WoL-флаги, bios, power, devices, session, autostart_nexus). Скрипты — константы; аргумент агента никогда не становится текстом скрипта.
- `run_command` — только `exe + массив аргументов` (`shell:false`): R0/R1 автономно, R2 (winget install `--id … --exact`, `git push`) и R3 (всё прочее) — согласие на **точный текст** команды; запрет при любом согласии: `-EncodedCommand`, скачать-и-выполнить, изменение Defender/UAC/Smart App Control/BitLocker/Firewall, хранилища и дампы учётных данных, автовход, разрушение диска/загрузчика. stdout/stderr с маскировкой секретов, exit code, timeout, cancel. STOP, пауза владельца, `finish_task`, отмена клиента убивают дерево процессов; конец lease (`view_idle`) — нет.
- `command_plan` — одобренный владельцем план привязан к SHA-256 (изменение = новое одобрение); шаги через `run_command planId` или **выполнение самим Host** без ходов модели; остановка при первой ошибке/STOP/паузе; шаг с неизвестным исходом после перезапуска **никогда не повторяется** автоматически; продолжение после перезапуска — только если владелец одобрил план с `resumeAfterRestart`.
- Лимиты из кода → профиль (`limits`: maxTasks, maxCopyMB, commandTimeoutSec, maxOutputKB, maxCommands); `taskRoots`, `allowedPackages`.
- Честная граница: процесс от имени владельца имеет все его права; класс решается по тексту запроса, поэтому R3 = «владелец видел точный текст».

### Блок 4. Файлы, загрузки, питание, вход (FR-04, FR-05, FR-07, FR-08; NX-052-16/17/20/25/27)
- `files_scoped` — абсолютные пути: в `taskRoots` автономно, вне — согласие на операцию+путь, защищённые — согласие + маскировка, исполняемые файлы — согласие с diff; create / replace-with-backup (проверка `expectedSha256`, бэкап, атомарная замена) / edit-copy / copy без перезаписи / delete в `.nexus-trash`.
- `download_verify` — https, публичные хосты (проверка DNS на каждом редиректе), лимит размера, явные состояния, SHA-256 (несовпадение → `.quarantine`), Authenticode и ожидаемый издатель, **Mark of the Web сохраняется** — Smart App Control/SmartScreen действуют как для браузерной загрузки.
- `power_action` — `lock`, `display_off` сразу; `sleep/hibernate/restart/shutdown` — по умолчанию dry run с предусловиями (несохранённые документы, автозапуск NEXUS при входе, канал входа владельца, независимое пробуждение); выполнение — согласие на конкретное действие, 60 с с отменой `cancel_shutdown`, без `/f`; `wake/power_on` → BLOCKED. Профиль: `lockAfterTask` (решение §0.1: без задачи — блокировка), `logonChannelVerified`, `wakeDevice`.
- **Sentinel** (`sentinel/nexus-sentinel.mjs`) — задача SYSTEM при загрузке: только слово состояния (`booting/logon_screen/locked/user_session/host_up`) в шлюз по отдельному токену; без ввода, экрана, команд и паролей. Шлюз: `/sentinel`, вердикт `awaiting_owner_logon` вместо безликого `pc_offline`.
- Шаблоны задач: `NEXUS-Host-Logon.xml` (при входе владельца, в его сессии, один экземпляр, перезапуск при сбое), `NEXUS-Sentinel.xml`. Автовход, пароли, `HighestAvailable` — отсутствуют (проверено тестом).

## BLOCKED / открытые решения
1. Пробуждение из сна/выключения — нужен независимый отправитель magic packet в LAN и, вероятно, Ethernet вместо USB Wi-Fi (решение и возможная покупка — владельца).
2. «Экран скрыт во время задачи» (§0.1) — `display_off` не держится при вводе; нужен curtain-режим удалённого рабочего стола (CRD) — не установлен.
3. Канал удалённого входа после перезагрузки (CRD → RDP через Cloudflare) — не установлен; требует системных изменений с разрешения владельца.
4. Подтверждение R3 сейчас идёт через `confirm_action` из чата (как в 0.5.2, ChatGPT в режиме «Always ask»). Более сильный вариант — подтверждение на странице Live View шлюза паролем владельца (вне текста агента) — спроектирован в архитектуре, не реализован.
5. Пункты 03, 05, 13, 19, 21, 26 требуют воспроизведения на реальных приложениях ПК владельца — сделать после установки по результатам приёмки.
