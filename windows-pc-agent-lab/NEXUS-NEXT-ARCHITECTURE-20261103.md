**Статус:** архитектура, разработка не начата. Рабочий Host 0.5.2 (`a22fae6`) и Gateway (`27d66b41…`) не меняются.
**Основа:** `NEXUS-NEXT-UNIFIED-TECHNICAL-SPEC-20261103.md` (ТЗ, `b3b16b7`) + ревью Claude 03.11 + уточнение владельца 03.11 (ниже — «Р1…Р5»). При расхождении с ТЗ действует этот документ.

## 0. Решения владельца (03.11.2026)
- **Р1.** Наличие возможности ≠ разрешение на рискованное действие. Широкие инструменты; обычное — автономно; критическое — с обязательной защитой.
- **Р2.** Число окон — регламент, не физический лимит. Многооконность с фокусом, ownership и последовательным закрытием.
- **Р3.** После перезагрузки вход выполняет владелец: на ПК или удалённо через защищённый экран входа на телефоне. **Автовход запрещён. Пароль агенту не передаётся.** Нужен отдельный механизм удалённого входа, работающий до пользовательской сессии.
- **Р4.** После входа NEXUS сам восстанавливает соединение и продолжает задачу с чекпоинта.
- **Р5.** Hard deny и технические лимиты пересмотреть: где безопасно — заменить регламентом и контекстным контролем. Защиту секретов, границы авторизации и критические необратимые действия не ослаблять.

## 0.1 Решения владельца по NEXT-2 (03.11.2026, ~09:44) — приняты
- **Вход:** сначала исследовать Chrome Remote Desktop, затем RDP через Cloudflare при необходимости. Автовход запрещён.
- **После отключения удалённого доступа Windows не должна оставаться доступной посторонним без авторизации.** Следствие: вариант A с `tscon` на разблокированную консоль **не принимается**. Техническое противоречие, которое нужно решить в NEXT-2: GUI-автоматизации нужен разблокированный рабочий стол. Проектное решение: (1) во время задачи NEXUS — рабочий стол разблокирован, как сегодня, а дисплей ПК выключается/скрывается (проверить: «curtain»-режим CRD, `display_off`); (2) без задачи NEXUS блокирует Windows (`LockWorkStation`), снять блокировку может только владелец через канал входа. Не проверено на ПК.
- **R0/R1** (read-only диагностика, обычные безопасные команды) — автономно.
- **R3** — согласие на конкретное действие **либо заранее одобренный неизменяемый план**. **Хеш плана — не подтверждение авторизации:** авторизация = явное одобрение плана владельцем через механизм согласия (consentId, вне текста агента); хеш лишь гарантирует, что выполняется тот же неизменённый план. Изменение плана → новое одобрение.
- **Отдельная учётная запись** — исследовать как изоляцию произвольных команд (R3/неизвестные), не ограничивая обычную автономность (R0/R1 идут от имени владельца).

## 2. Фундаментальное ограничение, которое определяет Р4
ChatGPT действует **только во время своего хода в чате**. Host не может заставить ChatGPT продолжить: после восстановления связи кто-то должен вызвать инструмент. Поэтому «продолжает сам» реализуется двумя слоями:
- **(а) Host-сторона (NEXT-1/2):** соединение, сессия и Live View восстанавливаются без участия владельца; задача — в состоянии `resumable` со своим ID; первый же вызов ChatGPT получает `resume_point` (что сделано и проверено, какой шаг следующий). Любое сообщение владельца в чате, даже «продолжай», достаточно.
- **(б) Локальный исполнитель плана (NEXT-2):** шаги, заранее записанные как план (например, «после перезагрузки: проверить X, запустить Y, собрать Z»), Host выполняет сам после входа — без хода ChatGPT, с тем же журналом/STOP/паузой. Нерешённые шаги (требующие рассуждения) ждут ChatGPT.
- Запуск ChatGPT по расписанию для продолжения — **не проверено**, может ли он вызывать MCP-коннектор вне живого чата. Не обещается.

## 3. NEXT-1 — автономность в пределах текущих полномочий (только Host + каталог Gateway)
Без новых системных прав, без изменений Windows. Зависимостей нет.

### 3.1 Задача отдельно от сессии (NX-052-04, 09, 31; FR-01.2, FR-07.3)
- **Задача** (`task_id`, план, чекпоинты, idempotency-журнал) живёт до `finish_task` / STOP / явной отмены / TTL задачи (по умолчанию 24 ч), переживает: конец lease, обрыв туннеля, перезапуск Host (уже на диске — `tasks/`).
- **Сессия** (lease) — только «сейчас идёт работа на экране»: Live View, ownership-окна. Конец lease ⇒ задача `interrupted → resumable`, не `closed`.
- Пока задача `running`, Live View держится по **task heartbeat** (любой вызов ChatGPT, включая read-only) с потолком 10 мин без вызовов; дальше — `view_idle`, кадров нет, задача сохраняется. Кадры по-прежнему не продлевают ничего (приватность).
- Возобновление: тот же `task_id`; сначала read-only сверка эффектов (окна, файлы, URL), затем только невыполненные шаги; аргументы, устаревшие после паузы (hwnd/координаты), перепроверяются — иначе `stale_args`.
- Статусы различаются: `view_idle`, `lease_expired`, `owner_paused`, `owner_stop`, `host_offline`, `tunnel_unavailable` (530), `awaiting_owner_logon`, `sleep`, `shutdown` — последние три определяются по данным NEXT-2 (§4.3); без них честно `host_offline`.

### 3.2 Многооконность по регламенту (Р2, NX-052-30, TEST-NEXT-01)
- `nexus_window_not_closed` **удаляется**. `nexus_window_unverified` и `nexus_verify_before_close` **остаются** (открыл → сделал → проверил → закрыл — регламент на каждое окно).
- `nexus_window_limit` → **мягкий регламент**: `windowBudget` в профиле (по умолчанию 4); превышение не запрещено, а требует в вызове `reason` (журналируется и видно на кадре Live View). Жёсткий потолок только защитный (16) — от зацикливания.
- Фокус: явный `focus_window` между своими окнами; ввод только в окно, которое NEXUS сам последним сфокусировал (как сейчас). Перенос через буфер — между своими окнами, с восстановлением буфера (+ нетекстовые форматы: image/HTML/files — через Java `Transferable` снимок).
- Закрытие: каждое окно закрывается сразу после окончания работы с ним; `finish_task` — сеть безопасности.

## 4. NEXT-2 — системные инструменты, вход владельца, восстановление после перезагрузки
Зависит от NEXT-1 (задача отдельно от сессии). Требует системных изменений на ПК — каждое по отдельному разрешению владельца.

### 4.1 Широкие инструменты под регламентом (Р1, Р5, FR-03)
Классы исполнения команд (каждая команда — `exe` + массив аргументов, без строки shell по умолчанию; stdout/stderr/exit/timeout/cancel/audit; привязка к `task_id`; STOP/пауза её убивают):

| Класс | Что | Как |
|---|---|---|
| R0 диагностика | Встроенные read-only инструменты Host: ОС, CPU/RAM/диски/SMART, процессы-дерево, службы, планировщик, автозапуск, сеть/драйвер/маршруты/DNS, BIOS/питание/wake, USB/BT, журнал событий (без текста сообщений с секретами) | Автономно. Не через PowerShell-строки: фиксированные запросы (CIM/WMI) внутри Host |
| R1 профили инструментов | `git`, `node/npm` в workspace, `winget list/search/show`, архиваторы, сборки; конкретные подкоманды — по таблице профиля | Автономно с аудитом |
| R2 изменения в границах задачи | Запись в файлы вне workspace в путях задачи, `winget install/uninstall` подписанного ПО (проверка подписи/хеша) | Автономно, если путь/пакет назван в поручении владельца; иначе — согласие на ресурс |
| R3 произвольная команда / системное изменение | PowerShell/CMD-скрипт, служба, планировщик (запись), реестр (запись), сеть | **Согласие на точную команду** (полный текст + последствия). «Подписанный план» = владелец одобрил хеш плана один раз → шаги, совпадающие с хешем, идут автономно |
| Запрет | `-EncodedCommand`, загрузка-и-исполнение (`iex(iwr…)`), отключение Defender/UAC/SAC/BitLocker/Firewall, чтение хранилищ паролей, экспорт учётных данных | Не выполняется ни при каком согласии из чата; только владелец сам |

Честная граница: запущенный от имени владельца процесс имеет **все права владельца** — `policy.mjs` не видит, что он читает. Поэтому R3 = согласие на точный текст, а не классификатор «по виду». Опционально (решение владельца): отдельная учётная запись Windows без доступа к личным папкам для R1/R2 — сужает ущерб от ошибки.

### 4.3 Вход владельца после перезагрузки (Р3) — механизм до пользовательской сессии
Без входа пользователя в Windows нет рабочего стола — Host (GUI) не может работать. Поэтому до входа работает только **слой 0**:
- **Слой 0 (служба, до входа):** `cloudflared` как служба Windows (отдельный туннель/hostname) + маленькая служба **NEXUS Sentinel** (без GUI, без команд): отдаёт состояние `booting / logon_screen / user_session / host_up` и время загрузки. Gateway показывает `awaiting_owner_logon` вместо безликого `pc_offline`. Sentinel не умеет вводить, не видит экран, не хранит паролей.
- **Канал входа (выбрать после проверки на ПК):**

| Вариант | Как | Плюсы | Минусы / проверить |
|---|---|---|---|
| **A. RDP через Cloudflare Tunnel + Access** | Remote Desktop (Win 11 Pro) включён только на localhost; tunnel-служба публикует его за Cloudflare Access (вход владельца: email-OTP/SSO). Телефон: Termux `cloudflared access rdp` → приложение Microsoft «Windows App» → localhost. Пароль вводится в RDP-клиенте на телефоне и уходит в Windows (NLA), NEXUS его не видит | Своя инфраструктура (Cloudflare уже есть), порт наружу не открывается, двойная аутентификация | После отключения телефона сессия RDP становится «disconnected» — без рабочего стола GUI-автоматизация не работает. Нужен перевод сессии на консоль (`tscon <id> /dest:console`, задача SYSTEM по событию отключения) — **консоль ПК остаётся разблокированной** (физический доступ к ПК видит рабочий стол). RDP требует пароль учётной записи (Hello PIN не подходит) — проверить тип учётной записи. Браузерный RDP Cloudflare — закрытая бета, не опора |
| **B. Chrome Remote Desktop** | Хост CRD как служба Windows; вход владельца — Google-аккаунт + PIN CRD на телефоне; затем экран входа Windows, пароль/PIN вводит владелец | Бесплатно, без своего туннеля и без RDP; сессия остаётся консольной (нет проблемы tscon); телефонное приложение готово | **Не подтверждено**, что CRD на Windows показывает экран входа после перезагрузки до входа пользователя — проверить на ПК. Зависимость от Google |

  Рекомендация: сначала **проверить B** (дешевле, не трогает сеть и права, консольная сессия). Если B не работает до входа — A.
- Запрещено (Р3): автовход, ARSO-вход по «use my sign-in info», хранение/передача пароля NEXUS, отключение Ctrl+Alt+Del/Secure Desktop.

### 4.4 После входа (Р4)
1. Задача Планировщика «При входе пользователя» (в его сессии) поднимает Host; повторный экземпляр не запускается (мьютекс/порт).
2. Host: самотест → регистрация туннеля → чтение `tasks/` → задача `resumable`, Live View готов → Sentinel фиксирует `host_up`.
3. Продолжение — §2: шаги локального плана выполняются сами, остальные — по первому вызову ChatGPT, с read-only сверкой эффектов и без повтора внешних действий (idempotency-ключи уже есть, N-08).
4. Перезагрузка, инициированная NEXUS (`restart`), — только при: нет несохранённых документов владельца, автозапуск Host проверен, канал входа §4.3 проверен. Это первый power-переход (AC-08: `restart → вход владельца → Host online → задача продолжена`).

**Приёмка NEXT-2:** TEST-NEXT-02, 06, 08, 09; AC-03, AC-04, AC-05; AC-07 включая реальный `restart` с удалённым входом с телефона.

## 5. NEXT-3 — питание и пробуждение (аппаратная зависимость)
Зависит от NEXT-2 (автозапуск + вход + resumable). `display_off`, `lock`, `sleep`, `hibernate`, `shutdown`, `wake`, `power_on` — по FR-08 ТЗ. Пробуждение требует **независимого устройства в домашней сети** (Host спит):
- Проверить фактический интерфейс: USB Wi-Fi DWA-182 (поддержка WoWLAN не найдена) или Ethernet Realtek на плате (WoL поддерживается платой; работа на этом ПК не проверена). Реалистичный путь — кабель Ethernet + BIOS ErP off + WoL в драйвере.
- Отправитель magic packet: роутер FASTWEB (если умеет WoL удалённо — не установлено), либо постоянно включённое устройство в LAN (старый Android с Termux / Raspberry Pi) с исходящим соединением к Gateway. Покупка — решение владельца.
- После пробуждения из sleep сессия пользователя жива (вход не нужен, если не требуется пароль при выходе из сна); после shutdown — снова §4.3.
