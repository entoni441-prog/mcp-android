# NEXUS NEXT — единое техническое задание на расширение автономности Windows

**Редакция:** 1.2, 03.11.2026 (Europe/Rome), расширение управления GUI на все обычные приложения (NX-052-34)  
**Статус:** ПОДГОТОВЛЕНО К ПЕРЕДАЧЕ РАЗРАБОТЧИКУ / РАЗРАБОТКА НЕ НАЧАТА  
**Рабочая ветка:** `experiment/nexus-0.5.2-owner-access-20261102`  
**Базовая версия:** NEXUS Host 0.5.2 + действующий NEXUS Gateway. Рабочее имя новой версии: **NEXUS NEXT**; окончательный номер релиза назначается после определения объёма.  
**Основной источник требований:** `NEXUS-0.5.2-ISSUES-AND-IMPROVEMENTS-LOG.md` — NX-052-01…31 и TEST-NEXT-01…10.

> **Граница полномочий этого документа.** Владелец одобрил накопление замечаний и формирование одного общего ТЗ. Этот файл сам по себе **не разрешает** изменение работающего NEXUS Host, Cloudflare Worker, Windows, BIOS, `main`, секретов, личных документов или выпуск в production. Начало разработки/развёртывания — отдельное поручение владельца. Продолжают действовать ранее выданные разрешения для обычных GUI-тестов и запреты на незапрошенное чтение секретов.

## 1. Цель и ожидаемый результат

Развить NEXUS из набора отдельных MCP-команд в **автономного, наблюдаемого и восстанавливаемого исполнителя на Windows 11**, которому владелец делегирует цель на естественном языке. Агент самостоятельно диагностирует состояние, планирует безопасные шаги, работает между несколькими приложениями и файлами, выполняет разрешённые системные команды, проверяет фактические результаты, очищает временные ресурсы, продолжает с чекпоинта после сбоя и предоставляет понятный отчёт.

**Формула выполнения:** принять цель → проверить предусловия и последнюю подтверждённую точку → включить Live View перед GUI → выполнить один контролируемый шаг → проверить результат → сохранить чекпоинт → продолжить → очистить созданные ресурсы → зафиксировать проверенное состояние. Никакой «успешности» по одному только `done:true`.

**Нецели:** обход защит OpenAI/коннекторов, снятие UAC/Windows Security/BitLocker, несанкционированный доступ к секретам, самостоятельные покупки или подписки, запуск скрытого мониторинга владельца, изменение production без поручения, собственный новый платный облачный стек при наличии работающей инфраструктуры.

## 2. Зафиксированная базовая точка (не переисследовать без причины)

1. **В рабочей сессии 02–03.11.2026:** Host `0.5.2` достижим через Cloudflare Tunnel, GUI-управление и собственный браузер доступны, однако `run_task=false`, `tasks=[]`, `process_control=false`. Из чата меняются только `gui_input` и `live_view`. Эти значения — **состояние последней проверки**, не гарантия на дату будущего релиза.
2. **Подтверждённые PASS:** открытие и закрытие собственных окон, Calculator `7+5=12`, Explorer drag/focus/navigation, свойства тестового файла, браузерные ссылки/вкладки, Selenium form input/select/checkbox с очисткой без Submit, системный File Picker для фиктивного TXT, ZIP compress/extract с проверкой SHA-256, операции с файлами внутри workspace, GitHub-журнал, журнал Host, восстановление cloudflared после сетевого тайм-аута.
3. **Подтверждённые ограничения:** принудительное правило «одно своё окно одновременно»; ложное `destructive_action` на кнопке «Очистить» Калькулятора; `browser_tabs list` выдаёт `internal_error` после закрытия последней вкладки; проблемы process/window ownership у Gemini/Steam/Explorer child; `foreground_lock_likely`/`csrss` в системном GUI; долгие Live-сессии завершаются idle lease; `open_app` для некоторых установленных приложений не работает; реальный STOP на телефоне не принят.
4. **Не подтверждено:** постоянный автозапуск Host после reboot; работа Wake-on-LAN именно по текущему интерфейсу сети; автономный подъём Host из выключенного ПК; полный DOCX/XLSX/PDF-цикл; полная разработка через IDE; работа в системных окнах повышенных прав. Исторический INSTALL-REPORT указывает на удаление временной задачи `NEXUS-Host-Run` — не путать с сегодняшней проверкой реестра автозапуска.
5. **Питание:** Windows 11 Pro, плата Gigabyte B550 AORUS ELITE V2, AMD Ryzen 7 3800X, BIOS AMI F19; прежний путь сети использовал USB Wi-Fi D-Link DWA-182. Поддержка WoL проводного LAN не доказывает пробуждение через USB Wi-Fi, а Cloudflare Worker не может сам доставить magic packet внутрь выключенной домашней сети.
6. **Внешняя граница:** попытка вызвать `open_app antigravity` была заблокирована средствами безопасности OpenAI до Host (NX-052-18). Нельзя считать это дефектом Windows и нельзя обходить блокировку альтернативным вызовом.
7. **Нельзя регрессировать:** защищённые ресурсы, редактирование/маскирование собственных и пользовательских вкладок Блокнота, запросы согласия на реальные разрушительные/финансовые действия, owner pause, физический STOP, раздельный браузерный профиль, восстановимая корзина, журнал без секретов и отсутствие действий после отмены.

Полная доказательная база и точные trace/error IDs остаются в первичном журнале; настоящее ТЗ — **нормализованный план работ**, а не замена первичных протоколов.

## 3. Приоритеты, стадийность и зависимости

- **P0 — обязательная безопасность и доступность:** STOP/Owner Pause; защита чужих окон и файлов; секреты/согласия; устойчивость Host/Tunnel и чекпоинтов; восстановление после теста; независимый доступ для power-тестов.
- **P1 — основная автономность:** диагностика и командный канал, несколько собственных окон, нормальный жизненный цикл приложений, доступ к файлам в пределах поручения, управление ПО, автозапуск, проверенное восстановление после перезапуска.
- **P2 — функциональные регрессии и удобство:** точная классификация кликов, стабильные вкладки/модальные окна, launcher для отдельных приложений, масштаб/координаты, просмотр системных страниц, периферия.
- **P3 — не блокирующие интеграции:** IDE-приёмка при наличии установленной IDE, ADB/scrcpy после проверки Android/Wi-Fi, UI-улучшения и аналитика журналов.

**Порядок реализации:** сначала изолированная среда и защитные инварианты → команды/диагностика и восстановление → приложения/окна/файлы/веб → автозапуск/питание/устройства → сквозная приёмка → отдельно разрешённый выпуск. Все пункты входят в **один согласованный backlog и одно ТЗ**, но не обязаны одновременно попадать в один production-release: допустимы тестовые этапы и отдельные релизные ворота.

## 4. Архитектурные контракты

### FR-01. Управление сессией, Live View и STOP (P0)

1. `watch_nexus` вызывается до **любого** удалённого GUI-действия; мобильное представление показывает курсор, управляемый процесс, состояние ACTIVE/PAUSED/STOPPED и средства Pause/STOP. Без подтверждённой трансляции **не начинать** управление экраном.
2. Пока задача исполняется, Live View должен оставаться активным или автоматически **переподключаться после обычного idle/transport timeout** без новой команды владельца. В случае настоящего offline — сохранять чекпоинт и не продолжать GUI-вслепую. Обязательное различение: `view_idle`, `lease_expired`, `owner_paused`, `owner_stop`, `host_offline`, `tunnel_unavailable`, `sleep` и `shutdown`.
3. **Физический STOP владельца имеет абсолютный приоритет.** Он завершает сессию, прекращает дальнейшие действия и отключает передачу кадров; автоматический reconnect **не снимает STOP**. Возобновление только после явного «продолжай» владельца с актуальной проверкой.
4. Owner mouse/key activity → sticky pause, NEXUS не печатает в чужом окне. Снятие паузы только по явной команде. При возобновлении — повторная идентификация окна и проверка, не устарели ли аргументы действия.
5. В ответе завершения: `session_id`, `task_id`, `reason`, `receivedAt`, `hostTotalMs`, `framesAfterStop` (строго 0), `cleanup.closed/left`, `lastCheckpoint` и список последствий, подтверждённых измерением. `finish_task` идемпотентен.
6. Live View не может непрерывно показывать кадры при настоящем sleep/shutdown. После восстановления питания создаётся **новая подтверждённая** live-сессия, привязанная к прежнему checkpoint.

**AC-01:** воспроизвести idle timeout → stream restored без нового GUI-действия; затем физический STOP в середине теста → 0 новых вводов и 0 кадров после Stop, не возобновлять до владельца.

### FR-02. Многооконное управление, ownership и ввод (P0/P1)

1. Отменить жёсткое правило «один NEXUS-window за раз» как функциональное ограничение. Разрешить 2+ task-owned окон и вкладок для рабочих сценариев, но **сохранять строгую атрибуцию**: origin launch ID → launcher PID → child PID → hwnd → tab ID → task ID.
2. Для UWP/Electron/PWA/Steam webhelper, дочернего Explorer после распаковки и File Picker распознавать фактическое окно, даже когда PID меняется. Отчёт `createdByNexus` не должен возвращать PID без работающего GUI как единственный идентификатор.
3. Перед вводом проверять foreground, hwnd/контроль, bounds, owner-activity, координатный scale. После клика проверять ожидаемое изменение; `done:true` означает только попытку, не функциональный PASS.
4. Cross-app clipboard: поддерживать перенос фиктивного текста/таблицы/изображения между своими окнами, сохранение и восстановление прежнего clipboard (включая нетекстовые форматы), отчёт об ошибках, без чтения не нужного для задачи содержимого.
5. Временное состояние своих окон сохранять как owned/scratch. Закрывать только окна и вкладки, открытые задачей, сразу после использования; при закрытии чужого требуется **конкретное** поручение владельца и безусловно сохраняется правило несохранённых данных. Исключить двойной запрос только потому, что приложение породило дочернее окно.
6. Сценарии диалогов: Open, Save As, Properties, Cancel, Yes/No, save prompt, consent, modal браузера; выход без оставленных окон. Режим GUI-инспекции системных приложений read-only доступен в обычном контексте; защищённый desktop/UAC не автоматизировать вслепую.
7. Не полагаться только на названия кнопок для оценки последствий (например, «Очистить» в Калькуляторе ≠ удалить пользовательские файлы). Классификация зависит от app + тип элемента + контекст + ownership + существующие данные.

**AC-02:** одновременно Calculator + scratch/editor; перенос тестового текста/результата; перемещение окна; open/save/cancel; очистка синтетического поля без grant; реальные опасные удаления по-прежнему требуют защиты; все окна закрыты, чужие целы.

### FR-02A. Доступ к GUI Claude Desktop при сохранении запрета CLI (P1, NX-052-01)

**Обязательное требование, ошибочно классифицированное в редакции 1.0 как внешний блокер.** Реальная ошибка 03.11.2026 исходила из NEXUS Host: `focus_window({pid:7712})` → `app_not_allowed: owner_handoff_required hard_deny`, trace `8757522a9057bdf4`. В существующем `nexus-host/policy.mjs` basename `claude` включён в `DENY_APPS`; это подтверждённая техническая причина запрета в исходной ветке. Доступ в установленном Host NEXT 0.6.0-next по-прежнему **BLOCKED**.

1. Классифицировать **Claude Desktop GUI** по доказуемой идентичности исполняемого файла/пакета/подписи и принадлежности окна; не приравнивать его к одноимённому CLI Claude Code, оболочкам и запускателям команд. Не давать `allow` по одному имени процесса.
2. Для идентифицированного GUI разрешить штатные `window_info`, `inspect_ui` (с редактированием приватного текста), `focus_window`, `mouse_action scroll/click`, `keyboard_action` по поручению владельца. Live View включать до ввода; STOP, owner pause, task window ownership, границы секрета и запрет незапрошенной отправки информации сохранить.
3. При неизвестной идентичности процесса, защищённом контексте, терминале/CLI или попытке вывода секретов — явный отказ без обхода механизма защиты. Внешние блокировки OpenAI классифицировать отдельно, не выдавать за дефект Host и не пытаться их обходить.
4. В экспериментальной ветке добавить unit/negative tests для GUI, CLI, masquerading `claude.exe`, неизвестного signer, owner pause/STOP и secret redaction; провести реальную E2E-проверку, прежде чем признавать пункт RESOLVED.

**AC-02A:** `watch_nexus` → идентифицированный Claude Desktop GUI → управление фокусом → несколько прокруток **фиктивного** длинного текста с визуально/структурно подтверждённым изменением позиции → отмена, если нужно → закрыть только окно, созданное NEXUS, не затрагивая пользовательские разговоры. CLI-сессии и подменённое приложение должны оставаться недоступными. Итог PASS только после реального контроля на установленной сборке.

### FR-02B. Универсальное управление обычными GUI-приложениями (P1, NX-052-34)

**Это общее требование, а не дополнительная частная настройка Claude.** Обеспечить единый механизм работы в **ChatGPT, Claude Desktop, Grok, Google Antigravity**, других доверенных AI-десктоп-приложениях/PWA/браузерных вкладках и обычных GUI-редакторах. Конкретные примеры не образуют закрытый allowlist. Исправление NX-052-01 — часть этого общего контракта; не ограничиваться четырьмя назваными программами.

1. **Input и навигация:** открывать/идентифицировать окно, выбирать корректную область, читать доступные UI элементы и текст в порученном scope, устанавливать фокус; прокручивать содержимое **вверх и вниз** в главном окне, вложенных панелях и виртуализированных лентах; писать, выделять, редактировать, стирать только свой тестовый текст, по необходимости копировать/вставлять, использовать обычные кнопки и меню. После каждого действия проверять действительный UI/визуальный результат и контекст окна. Скролл `done:true` без изменения позиции не является PASS.
2. **Политика не по одному basename:** проверять подпись/image path/package identity, HWND, PID/child process ownership, PWA/браузерную вкладку и контекст содержимого. Отличать подлинный Claude Desktop от Claude Code CLI. Unknown/signature mismatch/скриптовые оболочки/парольные окна/UAC по-прежнему запрещены; не обходить платформенные ограничения.
3. **Разделять степени действия:** ввод черновика ≠ отправка сообщения; обычный клик ≠ запуск команд; прокрутка ≠ чтение секретов. `send/submit/publish`, переход к выполнению кода или финансовое действие требуют самостоятельной оценки намерения, риска и ранее делегированных полномочий, а не автоматического действия в ходе GUI-теста. Пользовательские тексты, проекты, настройки не менять ради приёмки.
4. **Lifecycle:** всегда `watch_nexus` первым, Live View и STOP доступен, owner pause блокирует ввод, временный текст очищается, вкладки/окна NEXUS закрываются, окна владельца не закрываются. Отказ одного приложения не прерывает независимые тесты других; по каждому — отдельный исход.

**AC-02B:** отдельные E2E на ChatGPT, Claude Desktop, Grok, Antigravity и на одном другом доступном обычном GUI: открыть/фокус → фиктивный черновик → редактирование и очистка → scroll вниз и вверх на синтетическом длинном тексте → подтверждение смещения контента и восстановления позиции → cleanup; без отправки, установки/обновления и изменения реальных проектов. Негативные сценарии CLI masquerade, UAC, защищённых элементов, чужих окон, STOP. Матрица PASS/FAIL/BLOCKED по каждому приложению; **общий PASS только при прохождении полного набора и безопасности**.

### FR-03. Диагностика Windows без GUI и системные команды (P1)

1. Добавить **read-only инструменты** для версии Windows, CPU/RAM/disk/SMART при доступности, PID/process tree, services, scheduled tasks, Startup/Run, Event Log (без извлечения секретов), network adapters/driver/route/DNS, BIOS/UEFI metadata, доступных sleep-states, Wake settings, USB/Bluetooth/ADB status. Результаты структурированы и помечены временем и источником.
2. Добавить управляемое выполнение PowerShell/CMD/CLI из NEXUS по конкретной задаче владельца: **аргументы массивом или подписанный план**, stdout/stderr/exit code, рабочая директория, timeout, cancel, ограничения ресурсов, audit и checkpoint. Для команды нельзя молча использовать GUI терминал либо PowerShell окно. Процесс создаётся только авторизованным Host/runner и привязан к task ID.
3. Обычные диагностические, сборочные, Git/ADB и файловые операции в разрешённых директориях автономны в рамках поручения; не требовать повторного подтверждения каждого безопасного шага. Сетевые/системные изменения повышенного риска, отключение защиты, установка драйверов, изменения credentials и destructive write — отдельная проверка намерения и последствий по установленной матрице.
4. Текущие ограничения `run_task:false` / `tasks:[]` считать **дефектом покрытия возможностей**, а не разрешением обходить policy.mjs или системные защиты. Режимы `diagnostic-readonly`, `owner-task`, `elevated-handoff`; запрещённые OpenAI/OS действия не маскировать через альтернативный инструмент.
5. Для elevated action использовать owner handoff с отображением точной цели и запросом Windows UAC владельцу; не перехватывать пароль, не отключать Secure Desktop.

**AC-03:** прочитать Task Scheduler + сетевой адаптер без GUI; выполнить безопасную команду (например, read-only version в sandbox), получить точный stdout/stderr/exit, отменить длинную test task через STOP; попытка чтения секретного пути и изменения UAC без разрешения должна быть заблокирована.

### FR-04. Файлы и нативные документы (P1)

1. `files.task_scoped` расширить за workspace в пределах **целей владельца и явно выбранных путей**. Навигация/поиск/чтение/запись разрешённых файлов, metadata, PDF/DOCX/XLSX/PNG и вложений через соответствующее приложение и файл API — без широкого сканирования личных папок.
2. Режимы `read-only`, `edit-copy`, `replace-with-backup`. Для записи контролировать `expectedSha256`/version, атомарное сохранение, реальный diff/preview, восстановимую корзину или резервную копию; конфликт версии останавливает запись.

### FR-07. Автозапуск, задачи, recovery и отчётность (P0/P1)

1. В экспериментальном окружении проверить фактическую конфигурацию Task Scheduler, служб, Run/Startup и запуск двух процессов Host+cloudflared; исторический отчёт 0.5.2 сам по себе недостаточен.
2. Реализовать устойчивый запуск после **reboot**, с трассировкой процесса, политикой перезапуска, логами, самотестом, защитой от нескольких экземпляров. При GUI-управлении учитывать, что сервис до входа пользователя не равен доступной интерактивной сессии Windows.

Статусы `pending/running/paused_owner/waiting_owner/interrupted/failed/completed/stopped_by_owner` и чёткий следующий шаг. После reconnect сначала `read-only verify effects`, затем только невыполненные действия.
4. Для внешних эффектов (создание/отправка/платёж/удаление) idempotency keys; никогда не повторять действие после тайм-аута по одному предположению. Протокол «одна попытка + адресная диагностика» для неисправного канала: нельзя бесконечно расходовать ресурсы.
5. По поручению запускать задания/диагностику по расписанию, не дублировать существующие, запрашивать действие владельца лишь при разрешениях или реальном риске. Платные API/кредиты — без автоматических пополнений.
6. Аудит содержит `task_id`, источник действия, ID окна/файла, шаг, момент времени с зоной, статус, причину, затронутые ресурсы, проверку и последствия, но без текстов паролей/токенов/содержимого чужих документов.

**AC-07:** тестовое задание переживает restart самого Host, восстановление туннеля и timeout без двойной записи; после реального перезапуска Windows Host снова online и Live View запускается заново, но только когда этот этап безопасен.

### FR-08. Полный цикл питания и устройства (P1 с аппаратной зависимостью)

1. Различать и реализовать отдельные команды `display_off/on`, `lock/unlock` (unlock только через легитимную процедуру владельца), `sleep`, `hibernate` (если поддерживается), `restart`, `shutdown`, `wake`, `power_on`. Для каждой: предусловия, кто выполняет команду, статус принятия, фактический проверяемый переход.
2. **Независимое пробуждение обязательно.** Host на спящем/выключенном ПК не выполняет команды. Настроить локальный доверенный исполнительно-контрольный механизм (существующий совместимый роутер, постоянно включённое устройство LAN или подходящий штатный механизм), авторизованный удалённо и работоспособный без Windows Host. Без него нельзя обещать автономный `wake`/`power_on`.
3. Проверить текущий физический сетевой путь (USB Wi-Fi vs Ethernet), питание сетевого адаптера, BIOS/UEFI WoL, состояние S3/S4/S5 и поддержку устройства. 4. Перед reboot/shutdown/sleep — распознавание несохранённых пользовательских документов, проверка автозапуска Host/Tunnel, проверенный канал возврата, понятный аудит; не форсировать закрытие. При выключении Live View закономерно завершится. После пробуждения/загрузки — отдельная сессия и доказанный online.
5. По умолчанию режим `dry_run` с планом последствий для power-команд. Реальный тест только после AC-07 и успешного независимого пробуждения.

Выполнение зависит от физически подтверждённых возможностей.

## 5. Матрица разрешений и защиты

| Класс действия | Поведение | Примеры |
|---|---|---|
| R0: наблюдение | Автономно в рамках поручения, безопасный вывод | Системная read-only диагностика, список процессов, версия приложения |
| R1: обратимые обычные действия | Автономно с аудитом и очисткой | Управление кнопками своего окна, копия фиктивного файла, диагностическая CLI, очистка синтетического поля |

| R4: финансовое/публичное обязательство или секреты | Самостоятельно не совершать без отдельного подтверждения конкретного действия | Купить, оплатить, отправить третьим лицам, открыть/передать секреты |

**Важно:** пользователь ранее делегировал обычные GUI, диагностику, PowerShell и работу с порученными файлами; не спрашивать разрешение заново для каждого стандартного шага после реализации полномочий. Но это **не** равно разрешению на получение токенов/паролей, изменение UAC и выполнение платежей. Внешние политики OpenAI и ограничения OS выше Host: не обходить их.

**Двойная защита:** (а) policy-aware инструменты и следствие эффекта; (б) критические команды проверяются контекстом, task scope, владельцем и Windows permission. В рискованных случаях fail-closed. Ложные блокировки (NX-052-28) исправлять точечно, не отменяя защиту целиком.

## 9. Требования к качеству и Definition of Done

1. **Никаких секретов в аудитах, скриншотах и tool-output.** Защищённое содержимое не извлекается без цели/согласия; маскировка и отказ при сбое классификатора.
2. **Нет случайных эффектов.** Операции с файлами/сетью/браузером идемпотентны по последствиям, тестовые временные данные очищены или перемещены в recoverable trash с отчётом.
3. **Нет управления чужими окнами/данными.** Установлены HWND/task ownership, проверка foreground, обработка конфликтов и ошибок UAC, корректная реакция на owner activity.
4. **Непрерывность только там, где физически возможна.** Live View перед GUI; восстановление после тайм-аута и reconnect; STOP абсолютен; сон/выключение прерывают Live View законно.
5. **Точность статусов.** `started` не равно `finished`, `clicked` не равно `navigated`, `URL visited` не равно `downloaded`, `Host online` не равно `autostart confirmed`, `board WoL supports` не равно `current WoL works`.
6. **Не покупать новые ресурсы.** Существующие GitHub, Cloudflare, Android, Drive и другие уже подключённые средства используются по возможности. Новые тарифы/устройства — отдельное решение владельца.
7. **Тесты измеримы.** Для каждого требования указать реальный tool-call, expected/result, audit trace и автоматизированный тест; реальные GUI/STOP/power тесты отдельно от моков.
8. **Нет выпуска при P0 FAIL.** Любой FAIL в безопасности, STOP, чужих окнах/содержимом, сохранении данных или восстановлении — блокер. Отсутствие независимого wake блокирует только power acceptance, но не выпуск остальных функций, если power явно отключён.
9. **Rollback готов до deploy.** Резервная копия и SHA-256 рабочего Host, предыдущий Gateway/Worker, документированные restore steps без перезаписи других приложений; rollback не запускать автоматически без решения по конкретному инциденту.
10. **Финальная выдача:** исходники/тесты в экспериментальной ветке; changelog; протокол приёмки; список открытых отклонений; version/build/hash; runbook обновления и rollback; чёткий список новых MCP tools/permissions; результаты безопасности; контрольная финальная очистка.
