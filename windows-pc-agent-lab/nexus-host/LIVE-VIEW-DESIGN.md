# NEXUS Live View — проект (0.4.3 MVP), НЕ реализовано в 0.4.2

Цель владельца: в реальном времени видеть, что ChatGPT делает на Windows (экран, курсор, изменения), с телефона и с ПК, как LIVE у TinyFish.
Решение по объёму: P0 (согласие, фокус, pc_offline) не откладываются; Live View — отдельный этап.

## Что уже есть и что нет
- Есть: `capture_screen` — отдельный PNG по запросу ChatGPT. Не поток.
- Нет: потока кадров, курсора на снимке, страницы просмотра.

## Можно ли показать Live View прямо в чате ChatGPT — НЕ проверено
- Гипотеза: ChatGPT Apps (MCP с UI-компонентами) позволяют встроить HTML-виджет в ответ инструмента; виджет живёт в песочнице и может обращаться только к доменам, объявленным в метаданных ресурса (CSP).
- Если это подтвердится для нашего коннектора — вариант A (виджет в чате). Проверка: один инструмент `live_view` с ресурсом-виджетом и `connect_domains: [nexus-gateway…workers.dev]`; смотреть, рендерится ли он в веб-ChatGPT и в Android-приложении.
- Если нет — вариант B (гарантированный): ссылка из чата на страницу просмотра на шлюзе.

## Вариант B — архитектура (существующие компоненты, без платных сервисов)
```
Телефон/ПК (браузер) ──HTTPS──▶ nexus-gateway /live  (страница + вход владельца)
                                     │  GET /live/frame (после входа)
                                     ▼
                        quick tunnel ──▶ NEXUS Host /frame (Bearer NEXUS_TOKEN)
                                     ▼
                        Java Robot: кадр JPEG + курсор, ≤ 960 px, качество 0.6
```
- **Кадры:** опрос 2 кадра/с (настраивается 0.5–4), JPEG ~40–80 КБ → ~100–160 КБ/с. Курсор рисуется в кадр (Robot не захватывает курсор). Кадр берётся только пока страница открыта — нет зрителя, нет захвата.
- **Вход:** пароль владельца (тот же OWNER_PASSPHRASE, проверка и блокировка перебора через существующий Durable Object ConsentGuard) → cookie сессии HttpOnly/Secure/SameSite=Strict, 30 мин, подпись HMAC (ключ производный от NEXUS_TOKEN, новых секретов нет).
- **Разрешение:** новая capability `live_view` (по умолчанию false, переключение как gui_input: set_capability / файл), Host отдаёт /frame только при true.
- **Индикатор на ПК:** строка `LIVE VIEW: ON (зрителей: N)` в окне Host + запись в audit при старте/конце просмотра. (Значок поверх всех окон — отдельная задача, требует GUI-процесса.)
- **Пауза/STOP:** кнопки на странице; STOP = set live_view=false (мгновенно, без перезапуска). Закрытие окна Host выключает всё.
- **Без записи:** кадры не сохраняются ни на шлюзе, ни на ПК; `cache-control: no-store`.
- **Риски:** на экране могут быть пароли/личные данные — поэтому только владелец, только по паролю, только пока включено; ссылка без входа ничего не показывает. Трафик через quick tunnel — URL туннеля наружу не раскрывается (шлюз проксирует).

## Объём MVP (оценка)
Host: `/frame` + capability + индикатор (~120 строк, Java: курсор в кадр). Gateway: `/live` страница, вход, cookie, прокси кадра (~200 строк). Тесты: вход/блокировка, отказ без cookie, отказ при live_view=false, отсутствие кэширования, нагрузка 2 к/с. Поставка: Host + Gateway, одна активация.
