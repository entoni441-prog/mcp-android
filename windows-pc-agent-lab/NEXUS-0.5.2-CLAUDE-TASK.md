# NEXUS — пакет задач следующего обновления

**Статус:** согласованное техническое задание на разработку  
**Базовая версия:** NEXUS 0.5.1-b  
**Рабочая ветка:** `experiment/nexus-0.5.1-cleanup-stop-20261102`  
**Чекпоинт:** `92b848f`  
**CI:** `41410650907` — PASS

## 1. Главная цель

Реализовать режим **Owner Full Access + Protected Resources + Owner Handoff**.

NEXUS должен работать как полноценный технический помощник владельца Windows 11:

- Самостоятельно запускать установленные приложения.
- Управлять интерфейсами и выполнять обычные рабочие задачи.
- Работать с файлами и папками в пределах разрешённых операций.
- Запрашивать участие владельца только при действительно необходимых ограничениях.
- После ручного вмешательства автоматически продолжать работу с сохранённого этапа.
- Не требовать повторного разрешения на каждое обычное приложение.

**Принцип:** полный рабочий доступ по умолчанию, отдельное согласие для защищённых ресурсов и критических действий.

## 2. Универсальный доступ к приложениям

### Задача N-01 — Dynamic Application Access

Устранить необходимость ручного добавления каждого обычного приложения в `allowlist`.

Требования:

1. Обнаруживать установленные приложения Windows.
2. Запускать обычные приложения по запросу.
3. Управлять их GUI через существующие механизмы NEXUS.
4. Использовать приложения, которые уже запущены владельцем, с соблюдением правил защиты данных.
5. Не изменять постоянные разрешения на критические ресурсы без владельца.
6. Сохранять журнал действий без конфиденциальных данных.

Поддержать IDE, браузеры, офисные программы, редакторы, графические приложения, файловые менеджеры и другие обычные программы.

**Ограничение:** не обходить защиту Windows, UAC и запреты на доступ к секретам. Если операция недоступна технически — переходить к Owner Handoff.

**Приёмка:** обычное установленное приложение запускается и управляется без предварительного ручного добавления в список разрешённых.

## 3. Защита секретов и личных документов

### Задача N-02 — Protected Resource Access

Ввести централизованную политику защищённых ресурсов.

К ним относятся:

- Пароли и хранилища учётных данных.
- Bitwarden и аналогичные приложения.
- Токены, API-ключи, сертификаты и приватные ключи.
- Файлы конфигурации с секретами.
- Личные документы, отмеченные владельцем как защищённые.
- Другие ресурсы, явно отнесённые владельцем к защищённым.

### Матрица разрешений

| Действие | Разрешение |
|---|---|
| Перейти в защищённую папку | Автоматически |
| Открыть её окно в Проводнике | Автоматически |
| Читать содержимое файлов | Только согласие владельца |
| Просматривать секреты в приложениях | Только согласие владельца |
| Копировать или передавать секреты | Отдельное согласие на конкретную операцию |
| Изменять или удалять секреты | Отдельное согласие |
| Открывать обычные рабочие документы | Автоматически, если они не защищены |

**Критическое правило: право открыть папку не означает право читать находящиеся в ней файлы.**

### Технические требования

- Не выполнять автоматическое чтение защищённых файлов.
- Не извлекать защищённый текст через UI Automation, OCR, буфер обмена, файловые API или журналы.
- Не использовать снимки экрана для обхода запрета на чтение.
- Не индексировать и не отправлять секреты в модель без разрешения.
- Скрывать предпросмотр и содержимое защищённых окон до согласия владельца.
- Не анализировать даже автоматически появившиеся секреты.
- Учитывать, что названия файлов и миниатюры тоже могут раскрывать конфиденциальные сведения.

При открытии защищённой папки разрешается показать окно владельцу, но NEXUS не должен читать его защищённое содержимое. При невозможности скрыть чувствительные данные захват такого окна приостанавливается.

### Разрешение на чтение

Согласие должно содержать:

1. Какой документ или ресурс требуется.
2. Для какой задачи.
3. Что именно будет прочитано.
4. Как будет использована информация.

Разрешение действует только в согласованных пределах. Оно не превращается в постоянный доступ ко всем секретам.

## 4. Передача управления владельцу

### Задача N-03 — Owner Handoff

Реализовать передачу управления человеку в момент технического или защитного ограничения.

**Сценарий:**

1. NEXUS выполняет задачу.
2. Обнаруживает препятствие: UAC, пароль, 2FA, защищённое окно, отсутствие системного разрешения или другое действие, требующее владельца.
3. При возможности открывает соответствующее окно.
4. Показывает запрос владельцу с краткой инструкцией.
5. При необходимости приостанавливает захват экрана и ввод.
6. Владелец выполняет необходимое действие.
7. NEXUS проверяет успешность операции.
8. Работа автоматически продолжается с сохранённого чекпоинта.

Требования:

- Не начинать всю задачу заново.
- Не требовать повторного входа в уже авторизованные сервисы без причины.
- Не просить передавать пароль в чат.
- Не обходить системные механизмы безопасности.
- Не повторять уже выполненные действия.
- При отказе владельца корректно завершать или пропускать зависимый этап.

**Приёмка:** задача продолжается после ручного подтверждения без потери состояния и дублирования действий.

## 5. Централизованные согласия

### Задача N-04 — Consent Manager

Развить существующий механизм `consent_required` / `confirm_action`.

Разделить операции на три уровня:

**Уровень 1 — обычная работа:** выполняется автоматически.

**Уровень 2 — защищённый ресурс:** требуется согласие на чтение или изменение конкретных данных.

**Уровень 3 — критическая операция:** требуется отдельное подтверждение потенциально необратимого или финансового действия.

Для каждого согласия фиксировать целевое действие, объект, последствия, срок действия и принятое решение.

Запрещено трактовать разрешение на одну операцию как универсальное согласие на последующие защищённые действия.

## 6. Исправление Блокнота

### Задача N-05 — Notepad Privacy / A-02

**Обнаруженный дефект:** при создании тестовой вкладки Windows Notepad может автоматически восстановить пользовательский документ с паролем активации NEXUS.

Требования:

1. Создавать тестовые документы в изолированном безопасном контексте.
2. Не вызывать автоматическое раскрытие пользовательских вкладок с секретами.
3. Не читать содержимое автоматически восстановленных вкладок.
4. Закрывать через `finish_task` только созданные NEXUS вкладки и окна.
5. Не закрывать и не изменять пользовательские документы без разрешения.
6. Не терять несохранённые пользовательские данные.

**Приёмка:** создание и закрытие тестового документа не раскрывает пароли, не изменяет пользовательские вкладки и не оставляет созданных NEXUS объектов.

До устранения дефекта не проводить тесты, способные снова вывести пароль на экран.

## 7. Финансовая граница браузера

### Задача N-06 — Financial Boundary D2 / B-01

**Обнаруженное замечание:** на Demoblaze кнопка `Place Order`, открывающая форму оформления, была заблокирована как потенциальное финансовое обязательство.

Требования:

- Разрешать просмотр товаров, корзины и переход к оформлению без лишних подтверждений.
- Различать открытие формы и фактическое создание заказа.
- Требовать подтверждение перед оплатой, подпиской, переводом или созданием платного обязательства.
- При невозможности достоверно определить последствия сохранять безопасную блокировку.
- Не проводить реальную покупку во время тестирования.

**Приёмка:** известный безопасный переход к оформлению выполняется самостоятельно; действие, создающее обязательство, блокируется до согласия владельца.

## 8. Live View, Stop и завершение сессий

### Задача N-07 — Stop & Session Lifecycle

Сохранить подтверждённое поведение версии 0.5.1-b:

- Stop завершает активную сессию.
- Live View прекращает передачу кадров.
- `finish_task` очищает созданные NEXUS ресурсы.
- Пользовательские окна, вкладки и процессы остаются нетронутыми.
- Постоянные разрешения не сбрасываются после завершения задачи.

Добавить измерение полной задержки Stop:

- момент нажатия владельцем;
- получение события Host;
- прекращение передачи кадров;
- завершение сессии;
- подтверждение очистки.

Не путать время исполнения серверной команды с полной задержкой пользовательского интерфейса.

## 9. Сохранение состояния работы

### Задача N-08 — Task Continuity

Реализовать устойчивый чекпоинт задачи.

Сохранять:

- текущий этап;
- выполненные операции;
- ожидаемое действие владельца;
- созданные NEXUS ресурсы;
- необходимые зависимости;
- результаты проверок;
- ошибки и возможность безопасного восстановления.

После Owner Handoff продолжать работу с последнего подтверждённого шага.

Повторное выполнение операций с внешними последствиями без проверки запрещено.

## 10. Безопасность, очистка и аудит

### Задача N-09 — Isolation & Audit

- Отличать ресурсы NEXUS от пользовательских.
- Не завершать пользовательские процессы произвольно.
- Не захватывать защищённые экраны без разрешения.
- Не записывать в журналы пароли, токены, ключи или содержимое защищённых документов.
- Не выполнять необратимые операции без требуемого согласия.
- При ошибке выполнять безопасную очистку только собственных ресурсов.
- Сохранять возможность отмены и восстановления там, где это технически возможно.

Секреты не должны появляться в телеметрии, диагностике, ответах инструментов и отчётах.

## 11. План реализации

Разработка ведётся в отдельной экспериментальной ветке на основе подтверждённого чекпоинта.

**Этап 1 — Архитектура и тесты**

Проверить текущие механизмы разрешений, классификации ресурсов, сессий и очистки. Сформировать тесты новых политик.

**Этап 2 — Политика доступа**

**Этап 3 — Owner Handoff**

**Этап 4 — Исправления**

**Этап 5 — Приёмка**

**Этап 6 — Развёртывание**

Только после успешных тестов и отдельного разрешения владельца.

## 13. Критерии окончательной приёмки

Обновление может получить итоговый PASS только если:

- Обычные приложения доступны без индивидуальных повторных разрешений.
- Защищённые папки можно открывать без чтения их содержимого.
- Чтение секретных документов невозможно без отдельного согласия владельца.
- Owner Handoff работает и позволяет продолжить задачу.
- Пользовательские документы не раскрываются при создании тестовых окон.
- Финансовые операции имеют корректную границу подтверждения.
- Stop завершает сессию и Live View, задержка измеряется корректно.
- Очистка не затрагивает пользовательские данные.
- Регрессионные тесты Host/Gateway и существующих функций пройдены.
- Production не меняется до разрешения владельца.

## Аудит Claude (02.11.2026) — что учесть при реализации

1. **N-01 и HARD_DENY.** Сейчас в HARD_DENY есть `explorer`, `code`, `cursor`, `systemsettings`, `control`, `taskmgr`. Для N-01/N-02 нужен `explorer` (с защитой по N-02). IDE (`code`, `cursor`) содержат встроенный терминал: ввод в него = произвольный shell, то есть обход правила «произвольная команда только с согласия». **Решение владельца:** разрешать IDE полностью или с запретом ввода в панель терминала (определяется по UIA; проверить надёжность на реальном VS Code).
2. **N-02 — что можно гарантировать.** NEXUS контролирует только свои каналы: UIA-чтение, снимки/Live View, файловые API, буфер обмена, журналы. Снимки: окна защищённых процессов/папок закрашиваются по их прямоугольникам до отправки (включая имена файлов и миниатюры в Проводнике). Экран владельца NEXUS скрыть не может — показ владельцу допустим по ТЗ. Чтение файла защищённой папки без согласия → отказ на уровне files/UIA.
3. **N-05 / A-02 — причина (вывод, не проверено на ПК):** Блокнот Windows 11 при холодном старте восстанавливает прошлую сессию со всеми вкладками владельца, в том числе несохранёнными. Это поведение Блокнота: NEXUS его не отключает без согласия владельца (это настройка «При запуске Блокнота»). Варианты: (а) не запускать Блокнот холодным стартом для тестов: если процесса нет — scratch открывается в другом редакторе либо запрашивается Owner Handoff; (б) при холодном старте приостанавливать захват и UIA-чтение до подтверждения своей вкладки и не читать восстановленные. Предпочтительно (а) + (б).
4. **N-06 / B-01.** Demoblaze `Place Order` = `data-toggle="modal"` (открывает форму), обязательство создаёт `Purchase`. Исправление: элемент, который открывает модальное окно/диалог на той же странице (`data-toggle|data-bs-toggle=modal`, `aria-haspopup=dialog`, `aria-controls` → `[role=dialog]`), не создаёт обязательство → автономно. Остальная граница не меняется; при неясности — блок.
5. **N-07 — Stop.** Момент нажатия Stop Host не видит. Host фиксирует: получение `notifications/cancelled` (или его отсутствие → lease), остановку кадров, конец сессии, конец очистки. Полная задержка = отметка времени владельца (секундомер/запись экрана) + эти метки. Не выдавать серверное время за полное.
6. **N-03/N-08 — Owner Handoff:** запрос `owner_action_required` {что сделать, где, как проверим}; ввод и захват на паузе; проверка результата по UIA/состоянию (не по словам в чате); чекпоинт задачи в `%USERPROFILE%\.nexus-host\tasks\<id>.json` без секретов; операции с внешними последствиями помечаются idempotency-ключом и не повторяются без проверки.
