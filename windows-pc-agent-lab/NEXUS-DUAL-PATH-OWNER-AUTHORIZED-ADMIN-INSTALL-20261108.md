# NEXUS — два независимых способа разрешения установки и системных операций

Дата: 08.11.2026. Требование владельца. Архитектурное ТЗ, **не реализация**.
Ветка: `experiment/nexus-prelogin-reboot-access-20261108`. Production/Host/Gateway/main не изменены.

## Цель и точная семантика

У владельца два **параллельных и независимых** способа разрешить конкретную установку приложения:

**Режим A — разрешение в чате ChatGPT.**
Владелец явно пишет: «Разрешаю установить [приложение]». NEXUS проверяет издателя, пакет и ранее согласованные параметры, затем автономно устанавливает и конфигурирует приложение, проверяет сервисы/автозапуск/состояние. **Второе подтверждение в Live не требуется**, если всё укладывается в данное владельцем разрешение и в заранее установленную ограниченную OS-привилегию. Отклонения (иная программа, запрос оплаты, изменение защиты, потенциальное повреждение файлов, расширение полномочий) требуют отдельного разрешения.

**Режим B — разрешение в NEXUS Live.**
Владелец получает уведомление внутри чата и/или открывает отдельную компактную панель: проверенное название приложения, подписант, точная операция, срок и «Разрешить / Отклонить». После **аутентифицированного подтверждения владельцем** NEXUS выполняет ту же установку и проверки. Для обычной установки не требуется дополнительное разрешение в тексте чата. Подтверждение Live должно быть реальным, одноразовым, защищённым от подмены страницы/чужой сессии и не пересылать секреты модели.

**Оба режима** ведут в один и тот же проверенный исполнитель установки. Отдельные разрешения не должны образовывать цепочку «сначала чат, потом Live, потом ещё пароль владельца» для заранее утверждённого действия. Внешние сайты/файлы/сообщения не считаются владельческим разрешением.

## Архитектурная граница Windows

Согласие владельца в ChatGPT или Live **не превращает** пользовательский процесс в администраторский токен Windows. Нынешний NEXUS Host работает при Medium Integrity, SID Administrators = Deny Only. Проверенный Google MSI `chromeremotedesktophost.msi` завершился с Windows Installer Error 1925 и exit 1603 — недостаточно прав установить сервис для всех пользователей.

Предыдущий OS-owned Scheduler `schedule-os-owned-titlebar-v10.mjs` использует `RunLevel=LeastPrivilege`; его автономность после перезапуска Host **не означает elevated/install privileges**. НЕ пытаться повысить существующий least-privilege task, создавать SYSTEM-task от агента, отключать UAC, внедрять ввод в Secure Desktop или превращать одобрение в чате в обход OS-защиты.

**Необходимый компонент:** отдельный доверенный, ограниченный `NEXUS Installer Broker` (Windows service или согласованный enterprise-managed helper), с минимальным привилегированным API строго для одобренных операций. Для **первой установки** такого компонента требуется настоящая административная авторизация Windows (например, одно локальное подтверждение UAC) или уже существующий доверенный административный канал. Это начальный provisioning, а не подтверждение каждого будущего пакета.

## Минимальная политика Installer Broker

1. Вызов `install_verified_msi` или `install_verified_exe`, **никакого произвольного elevated shell**. Политика допустимых издателей и типов пакетов, проверка Authenticode, скачивание с официального HTTPS-домена, SHA-256/размера, защитные download-флаги, отсутствие небезопасных аргументов MSI/EXE.
2. Проверка аутентичности владельца, происхождения разрешения (A/B), границ действия, exact package artifact и срока. Одноразовый nonce/ID, защита от повторного выполнения и зависимости от устаревшей сессии; цифровая подпись/аутентифицированный канал между NEXUS Gateway/Host и Broker.
3. Broker исполняет только утверждённый install plan; ограничения на файлы и пути, отсутствие необоснованной передачи системных полномочий; верификация версии, службы и настроек, подробный журнал **без секретов**, достоверный успешный результат.
4. В случае неизвестного исхода **не повторять** опасный шаг автоматически. До установки — checkpoint и отказ без изменения, после — проверка состояния, восстановление/откат если возможно.
5. Аутентификационные данные Google, Windows PIN, пароли и ключи вводит владелец **только в доверенном UI**, не в chat, MCP-аргументы, CI, логи и репозиторий.
6. STOP, отзыв разрешений, время жизни привилегированной операции, защита от подмены URL/пакета, отклонение попытки расширить scope. Отдельное review Claude на code/diff и безопасности перед первым production provisioning.

## Этапы и acceptance

1. **Проектирование:** определить Windows-supported способ создания Broker и точный owner authorization contract; провести threat model и независимое review; реализовать в экспериментальной ветке с mock/Windows tests, не подменяя реальный UAC.
2. **Первичный onboarding (один раз):** пользователь подтверждает стандартный UAC непосредственно на ПК либо через уже доверенный OS-admin capable канал; проверить подпись, ACL, Windows service identity, отказ от произвольного кода.
3. **E2E A:** владелец даёт разрешение **только в чате**; безопасный тестовый подписанный пакет устанавливается, настраивается и проверяется без Live-одобрения.
4. **E2E B:** владелец даёт разрешение **только через Live**; аналогичный тест проходит без отдельного «разрешаю» в чате. Если Live недоступен, режим A по-прежнему работает (при условии доступности установленного Broker).
5. **Negative:** чужая команда, поддельное сообщение/страница, неразрешённый издатель, installer switch с секретами, смена SHA, expired consent, неизвестный outcome, попытка shell/UAC bypass — fail closed.
6. **После PASS:** установить Chrome Remote Desktop через Broker, настроить trusted owner account, проверить доступ с Samsung к Windows logon screen, затем controlled reboot и восстановление NEXUS. Не заявлять проход до реального E2E.
