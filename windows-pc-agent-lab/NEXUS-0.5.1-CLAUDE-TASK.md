## Проверенный чекпоинт — не начинать заново
- На ПК Host NEXUS **0.5.0**. В этой сессии ChatGPT вызвал `get_capabilities` и `host_diagnostics`: `live_view=false`, `gui_input=false`, Host online, config `fileError=null`. Никаких дополнительных изменений на ПК не выполнялось.
- Живая приёмка 0.5.0: Host/34 доступных модели инструмента, Gateway online, встроенный `watch_nexus` и поток кадров (274 кадра), мышь/клавиатура/Notepad/Calculator — PASS; на чужой вкладке Notepad `consent_required` и `confirm_action(cancel)` — PASS, пользовательские вкладки сохранены.
- НЕДОРАБОТКИ из приёмки: `focus_window` Notepad `focused=false`, хотя клик помогает; собственная изменённая scratch-вкладка вызывает диалог сохранения; у Calculator `createdByNexus.windows=[]`; курсор именно *в live-клиенте* не подтверждён; браузер был отключён, Edge cleanup в тестах вызывает вопросы; штатная кнопка Stop ChatGPT → прекращение работы NEXUS НЕ проверена.
- **Новый воспроизведённый пользователем дефект:** после нажатия Stop на наблюдательном экране Live View оставался работать; после обычного финального отчёта Live View 0.5.0 оставался `live_view=true`. Сейчас отключено; нужна автоматическая гарантия, а не ручной Stop.
- Исходники и отчёт 0.5.0 уже в репозитории: `windows-pc-agent-lab/NEXUS-0.5.0-REPORT.md`, `NEXUS-0.5.0-ACCEPTANCE.md`; использовать рабочий код, не переписывать систему и не повторять всю историческую приёмку.


## ДОПОЛНЕНИЕ ВЛАДЕЛЬЦА 02.11.2026 — ПОСТОЯННАЯ АВТОНОМИЯ (ПРИОРИТЕТ НАД ОГРАНИЧИТЕЛЬНЫМИ ФРАЗАМИ В ЭТОМ ТЗ)

**Согласованная модель: владелец заранее задаёт границы, NEXUS автономно действует внутри них.** Владелец наблюдает в Live View, может остановить, уточнить либо впоследствии запретить конкретные действия. Не превращать работу в цепочку «разреши каждый клик/сайт/программу/обычную настройку». Не заменять контроль владельца отсутствием защит от действительно значимых рисков.

### D1. Постоянные полномочия vs временное выполнение задачи
1. Разделить в коде **постоянную политику полномочий владельца (persistent grant)** и **временную рабочую сессию агента (active task / lease)**. Постоянные разрешения сохраняются между задачами, чатами и перезапусками, пока владелец не изменит их. GUI-сессии, курсор/клавиатура, поток Live View, временные процессы и вкладки имеют собственный lifecycle.
2. В рамках заранее выданного постоянного доступа автоматически открывать приложения, сайты, браузеры, читать интерфейс, управлять окнами и файлами, изменять **обычные обратимые настройки Windows**. Не просить каждый раз включить \`gui_input\`, \`browser\` или разрешить типовое приложение. Реализовать понятную настройку классов разрешённых действий владельцем, без ручной правки JSON на каждый случай.
3. **Важно для безопасности:** «постоянно разрешён ввод» НЕ значит «постоянно включён захват и неограниченная фоновая работа». При завершении любой задачи рабочий lease заканчивается, все начатые NEXUS действия прекращаются, Live View на источнике становится **неактивен/выключен** и кадры не генерируются. Постоянный grant при этом НЕ отзывается — следующее разрешённое задание может стартовать автономно без нового согласования. Уточнить модель capabilities/API, чтобы \`get_capabilities\` не смешивал grant с текущей активностью. Действующий пункт о \`gui_input=false\` в финале относится к **эффективной активности завершённой сессии**, а не к отзыву постоянного разрешения.
4. Live View при реальном GUI-взаимодействии стартует автоматически **до** действий, остаётся видимым на протяжении GUI-задачи и **обязательно выключается по окончании каждой задачи**, при ошибке/отключении/Stop. Простые ответы, API и чтение серверных журналов не требуют экранного стрима. Не добавлять новых кнопок STOP — использовать штатную кнопку ChatGPT и доказуемый fallback TTL/watchdog, если сигнал остановки не доступен.
5. Никакой постоянный grant не разрешает произвольный удалённый shell, отключение Windows Defender/UAC, чтение паролей или обход HARD_DENY. Предусмотреть управляемое владельцем расширение обычных приложений и обычных настроек, отдельную безопасную модель для чувствительных категорий.

### D2. Финансовые действия — автономно до границы обязательства
- **Можно без повторных согласований:** поиск товаров и услуг, сравнение, подбор, получение цен, выбор вариантов, формирование корзины, переход к оформлению, подготовка формы.
- **Только после отдельного явного согласия владельца:** финальное действие, которое **создаёт платное обязательство**, включая заказ «оплатить позже», подписку/автопродление, покупку, выставление платного заказа или списание. Определять границу по результату действия, а не по тексту кнопки: «Разместить заказ» может создать обязательство до непосредственной оплаты.
- Банковские реквизиты, пароли, 2FA/коды подтверждения вводит владелец; агент не считывает, не сохраняет и не пересылает секреты. Не подключать платные ресурсы или услуги без согласия.
- На ненадёжных/необычных сайтах, при неизвестном получателе, сомнительной ссылке либо риске передачи секретов — остановиться и спросить согласие; обычный просмотр известных сайтов разрешён автоматически.

### D3. Другие значимые действия
- Постоянная политика определяет, какие действия обычные и обратимые, а какие требуют одобрения: необратимое удаление **важных пользовательских файлов**, массовые разрушительные операции, публичные публикации/сообщения **от имени владельца**, передачу персональной/конфиденциальной информации, смену критических политик безопасности.
- Обратимые изменения обычных настроек Windows, работа с файлами в согласованных местах, обычная навигация и оформление черновиков автономны; перед действительно необратимым внешним действием — отдельное согласие по принятой политике.
- Продолжить сохранять точечное согласие при закрытии **чужих/неизвестных** окон и вкладок с возможной потерей несохранённых данных. Собственные окна и вкладки NEXUS по завершении автоматически убирает.
- Владелец вправе прямо в ходе тестов задавать исключения/запреты; сохранять эти правила и применять далее без повторной настройки. Не добавлять запреты «на всякий случай» сверх реально обоснованных рисков.

### D4. Приёмка постоянных разрешений
- Владелец один раз настраивает автономный профиль: браузер + обычные приложения + стандартные обратимые Windows Settings. Две последовательные задачи проходят без нового запроса grant и без ручного редактирования \`capabilities.json\`.
- Начало каждой GUI-задачи автоматически включает временный Live View; её окончание (успех/сбой/Stop) прекращает трансляцию и активность на Host. Тест проверяет разницу \`persistentGrant=true\` vs \`activeSession=false\` после завершения.
- Обычные действия (поиск, браузер, открытие приложений, создание черновика, безопасные настройки) проходят без подтверждения на каждый шаг. «Оплатить потом», оформить платный заказ и подписку без явного согласия — НЕ проходят. Владелец может отменить.
- Тесты закрытия/удаления/публикации подтверждают границы, журнал и отсутствие потери пользовательских данных. При возникновении ошибки сначала диагностика и восстановление, потом точечный патч.
- Любые изменения текущих permission defaults, GUI/Windows Settings и допускаемых действий разрабатывать и тестировать только в экспериментальной ветке; НЕ включать новые production-полномочия самовольно до одобренной поставки/настройки владельцем.

**Главный приоритет этого дополнения:** NEXUS — автономный исполнитель под наблюдением и с управляемыми исключениями, а не система мелких подтверждений. Поддержать 0.5.1 как единый пакет, не создавать очередную серию версий.

### D5. Дополнительное уточнение владельца (02.11.2026): закрытие его окон по просьбе
- Владелец прямо поручил закрыть своё окно или вкладку → NEXUS вправе выполнить закрытие без вторичного формального согласия на то же действие. Если цель названа неоднозначно, сначала уточнить, какое окно имеется в виду.
- Без прямой просьбы владельца его окна остаются открытыми; уборка после задачи касается только окон, созданных NEXUS.
- При несохранённых пользовательских изменениях не соглашаться на потерю содержимого автоматически. Если выбор «Сохранить / Не сохранять / Отмена» не был указан в просьбе, запросить именно этот выбор, а не разрешение закрыть ещё раз.
- Добавить автоматические тесты обоих случаев: прямое поручение владельца закрыть собственную вкладку исполняется без повторного запроса; при отсутствии поручения — закрытие требует согласия. Проверить диалог несохранённых изменений.

## ОБЯЗАТЕЛЬНАЯ политика: «пришёл → выполнил → убрал за собой → отчитался»

### A. Live View lifecycle (P0, главное)
1. **Начало работы с настоящим рабочим столом Windows:** Live View включается автоматически **до первого действия мышью/клавиатурой/управления окнами**, чтобы владелец мог наблюдать. При простой беседе, чтении логов/API без GUI захват экрана НЕ запускать. Если владелец явно выключил Live View или не хочет трансляцию — уважать это.
2. **Во время действительной GUI-задачи** поток обновляется непрерывно, включая переключение между окнами. Не нужно открывать отдельные параллельные окна или вкладки просмотра; использовать уже внедрённый ChatGPT-виджет и существующий fallback `/live`. Не добавлять новые STOP-кнопки: владелец уже имеет штатный Stop в ChatGPT.
3. **Завершение КАЖДОЙ GUI-задачи (100%, даже если остались окна просмотра):** автоматически прекратить генерацию кадров на Host, установить `live_view=false` (если не зафиксировано явное требование владельца оставить), проверить факт остановки, только затем выдать финальный отчёт. Активный виджет/вкладка в ChatGPT НЕ должны сами по себе удерживать захват после окончания задачи. Нет зрителя → нет кадров.
4. **Любая ошибка, таймаут, обрыв соединения, остановка ответа ChatGPT, исчезновение клиента или закрытие сессии:** fail-safe остановка экрана и GUI-операций, а не вечный оставшийся `live_view=true`. Сделать независимый от доброй воли модели lifecycle на Host/Gateway: ограниченный срок аренды GUI-сессии (lease), heartbeat **от активной работы**, watchdog/TTL, отмена pending jobs, освобождение ресурсов. Сам просмотр кадров не должен бесконечно обновлять lease выполнения задачи.
5. **Штатная кнопка Stop ChatGPT:** выяснить, передаёт ли клиент событие остановки по MCP, abort HTTP/закрытие stream, lifecycle виджета. Если реально нет независимого сигнала, **не обещать мгновенный STOP**; сделать гарантированный короткий предел автоматического прекращения через lease (целевой максимум 10–15 с после потери активной работы, уточнить по безопасной технической реализации) и явно сообщить измеренную задержку. Stop должен прекращать не только визуализацию, но и дальнейшие операции, которые агент успел поставить в очередь (без закрытия чужих документов).
6. После завершения, STOP или ошибки: не делать автоматическое `live_view=true` повторно без новой GUI-задачи. Завершение рендеринга/ответа не должно оставлять активный поток.

### B. Уборка окон и вкладок (P0)
1. **Открыл собственное окно/вкладку → выполнил часть работы → закрыл**, если больше не используется. Не накапливать много окон; обычно одно, два или больше — только при реально необходимой одновременной работе.
2. На выходе из задачи (успех/ошибка/Stop) автоматически закрывать только NEXUS-created окна/вкладки/браузерные временные вкладки и ненужные собственные процессы. **Окна и вкладки владельца МОЖНО закрывать по его прямой просьбе — такая просьба уже является согласием, не требовать повторного подтверждения одного и того же действия.** Без просьбы владельца их не закрывать, даже если они в том же процессе Notepad. Если пользовательские данные несохранены и способ закрытия может привести к их потере, не выбирать «Не сохранять» без явного решения владельца.
3. В Windows 11 Notepad собственная `.nexus-scratch` вкладка после тестового ввода должна закрываться автоматически, без зависшего Save/Don't save. Допустимо автономно «не сохранять» только удостоверенно собственный одноразовый документ, который пользователь не редактировал; при неясном владении или возможных пользовательских изменениях — не уничтожать данные, попросить решение. Проверять вкладку по идентичности, а не только PID или имени.
4. Исправить `createdByNexus.windows=[]` у Calculator, отслеживать свои HWND/процессы при асинхронном открытии; обеспечить корректную идентификацию закрываемой цели и отсутствие влияния на чужие окна.
5. Убирать собственные Edge и дочерние процессы с отладочным портом, когда браузерная задача закончена, включая error/Stop, без убийства пользовательских Edge. Сохранять защищённую границу профиля.

### C. Прочие выявленные дефекты 0.5.0 (P1 — в том же пакете)
- `focus_window` на Windows владельца: точно определить, почему `focused=false`; проверять HWND, использовать безопасный fallback, не вводить в чужой процесс, возвращать реальное состояние.
- Отображение курсора в живых кадрах: подтверждение именно в ChatGPT web/Android (если без пользователя нельзя — готовый одноразовый шаг приёмки; не заявлять PASS из одних unit-тестов).
- Провести браузерный smoke в изолированном профиле с разрешением владельца **после установки**, проверить очистку процессов. Управление Windows Settings расширять через существующий механизм allowlist/consent, без обхода системных запретов и отключения защиты.
- Сохранять автономию пользователя: **не спрашивать согласие на каждый клик**. Запросы только для обоснованно опасных/необратимых действий (платёж, удаление чужих данных, секреты, сомнительные сайты) или существующей защиты чужих вкладок. Уже действующее право управлять ПК не должно требовать повторного одобрения каждой операции.

## Конкретная техническая приёмка и критерии PASS
Автоматические CI на Windows + Linux + Gateway, включая тестируемые lifecycle/lease/timeout, cancel, ownership/cleanup Notepad, Calculator, Edge без пользовательских файлов. Не запускать real-GUI тесты от обычного `node --test` без явного имени `*-real*`/отдельной метки. Не создавать бесконечный Java/Edge child.
В одной живой интеграционной проверке после установки:
- Запуск GUI-задачи → Live View включён до первого реального взаимодействия.
- Несколько действий подряд → Live View продолжает работать, число окон не растёт бесконтрольно.
- Финальный отчёт → `live_view=false`, кадров больше нет, свои вкладки закрыты, `gui_input=false` (если больше не нужен), пользовательские вкладки не тронуты.
- Прерывание задачи штатной кнопкой ChatGPT Stop → замерена задержка прекращения Host-контроля/потока; реальный PASS только если Host перестал выполнять операции и остановил захват. Если клиент не передаёт сигнал, зафиксировать правдивый worst-case TTL, а не «Stop гарантированно мгновенный».
- Сбой/отключение туннеля → watchdog отключает захват, никаких незавершённых фоновых процессов и чужих закрытых окон.
- Переключение между Notepad/Calculator, закр. только собственных scratch и окон; чужие документы — без изменений.
- Нет новой платной инфраструктуры, постоянных записей кадров, секретов в логах или новых кнопок STOP.
